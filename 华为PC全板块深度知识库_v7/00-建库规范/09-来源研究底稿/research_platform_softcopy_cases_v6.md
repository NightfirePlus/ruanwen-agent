> 研究日期：2026-10-17  
> 用途：为知识库补充可核验的软文案例、平台写法和风险边界；不用于直接复制原文。  
> 样本口径：优先品牌官网、品牌官方社交账号、平台官方案例页、权威媒体及公开可访问的实测内容。页面未公开首发日时，日期标为“持续更新；检索日 2026-10-17”。  
> 重要说明：微信视频号的单条内容通常缺少稳定、可匿名访问的网页链接，因此该部分明确标为“跨平台适配参照”，不能冒充微信原帖。发布前仍应在品牌官方视频号内搜索并核对原片。

### A. 公众号长图文（5 条）

#### 01｜折叠电脑研发幕后故事
- **平台 / 主题 / 产品场景 / 受众：** 公众号长文适配；MateBook Fold 设计研发；高端新品与工艺故事；科技爱好者、设计从业者、品牌用户。
- **标题机制：** 用“产品结果 + 幕后过程”制造信息差，不先堆参数。
- **结构：** 成品亮相 → 难题 → 多轮验证与工艺取舍 → 最终方案 → 品牌观点。
- **图文节奏：** 每个研发难题配一张结构、工艺或样机图；两至三段后用小标题换气。
- **证据类型：** 官方内部人物叙述、工序数量、研发过程、产品实物。
- **CTA：** 引导查看产品页、发布会或到店体验折叠形态。
- **风险点：** 研发数字和“首款”类表述必须回到原始版本核验；不能扩写未公开技术细节。
- **URL / 日期：** https://www-file.huawei.com/admin/asset/v1/pro/view/ec72c66222c849b9a62d6f43caa4222b.pdf ｜《华为人》第379期，2025。

#### 11｜618 华为 Linux 笔记本怎么选

- **证据类型：** 官网规格、版本差异、价格截面、使用任务。
- **CTA：** 去线下体验、核对销售版本与软件清单。
- **风险点：** 价格会过期；系统安装、授权和售后不能模糊处理。

## 三、各平台可复用框架

### 1. 公众号长图文

**推荐骨架：**

1. 具体人物在具体时刻遇到的问题；
2. 原来的处理步骤与卡点；
3. 产品怎样减少步骤；
4. 用三项可核验事实说明为什么；
5. 哪些条件下成立、哪些任务不适合；
6. 观看演示、查兼容表或到店体验。

**建议节奏：** 1200—2200 字；5—8 个小标题；每 180—250 字至少有一张与段落直接相关的图。封面只表达一个主题。

### 2. 新闻稿

**推荐骨架：** 标题写动作与对象；首段回答谁、何时、发布什么、面向谁；随后依次写核心变化、场景价值、权威引语、价格/渠道、脚注与媒体资料。

**证据要求：** 型号、发布日期、售价、上市渠道、测试条件、引语身份都能回查。形容词不能替代事实。

### 3. 知乎

**推荐骨架：** 先说结论 → 定义选择条件 → 按预算/任务分支 → 给证据 → 明确不足 → 给适用/不适用人群 → 提醒价格与版本时点。

**标题方式：** 沿用真实问题，不另造宏大标题。对比时先固定价格、配置、软件和测试条件。

### 4. 小红书

**推荐骨架：** 生活情绪或任务钩子 → 一天/一次任务过程 → 2—3 个功能自然出现 → 实拍结果 → 限制/踩坑 → 收藏清单或评论问题。

**图文节奏：** 6—10 张；首图只留一个结果；第二张交代人群与任务；中段每张解决一个问题；末图是核对清单。避免九宫格每张都塞参数。

### 5. 微博

**推荐骨架：** 节点一句 → 三条卖点短句 → 一张到六张顺序图 → 一个话题 → 一个互动动作。

**控制项：** 每条只承载一个传播目的。价格、抽奖和权益必须带有效期与规则链接。

### 6. 通用短视频

**推荐骨架：** 0—3 秒结果/动作 → 3—10 秒说明问题 → 10—40 秒演示 → 40—55 秒证据与条件 → 55—65 秒适合谁和 CTA。

**画面要求：** 真机、屏录、字幕三者对应；型号和系统版本第一次出现时打全；异常不要用跳剪遮掉。

### 7. 视频号

**推荐骨架：** 熟人式口播问题 → 一次完整操作 → 讲清限制 → 提醒转发给同事/家人 → 门店或顾问承接。

**区别：** 相比抖音减少强刺激标题，增加讲解和可信身份；相比 B站缩短测试维度。所有案例上架前在官方视频号内再次核验素材来源。

### 8. 抖音

**推荐骨架：** 前三秒展示矛盾或结果 → 单任务演示 → 前后对比 → 配置/版本字幕 → 评论区收集下一任务。

**风险控制：** 价格钩子实时核价；专业软件必须写版本和文件规模；不得截取评论当事实。

### 9. B站

**推荐骨架：** 争议问题 → 测试设计 → 分章节数据 → 真实工作流 → 优缺点 → 适用人群 → 完整数据表。

**时长不是目标：** 以任务完整度决定长度。章节、配置表、测试环境和原始结果比情绪表达更重要。

### 10. 直播

**推荐骨架：** 3 分钟说明本场解决什么 → 人群轮廓 → 连续场景演示 → SKU 区分 → FAQ → 权益核验 → 售后与退出机制。

**场控清单：** 型号卡、价格更新时间、库存状态、演示账号、备用网络、错误纠正话术、评论风险词。

### 11. 门店长图

**推荐骨架：** 首屏一句定位 → 6 个以内核心卖点 → 设计 → 任务场景 → 数据证据 → 版本差异 → 服务 → 脚注。

**图文规则：** 一屏一结论；参数旁边直接放测试条件；不同 SKU 用清晰表格，不把多个版本拼成一台“全能机”。

### 12. 销售朋友圈

**推荐骨架：** 一个具体人群 → 一个任务 → 三项证据 → 一项限制 → 私聊所需信息（预算、软件、设备、时间）。

**建议：** 80—180 字，3—5 张图；不公开客户资料，不刷屏，不使用未经核实的限时价，不写“闭眼入”“绝对不卡”等承诺。

### 13. 企业采购方案

**推荐骨架：** 现状盘点 → 业务与合规挑战 → 用户角色 → 方案架构 → 兼容/安全/运维 → 试点计划 → 验收指标 → TCO → 风险与退出 → 服务。

**证据要求：** 成功案例只证明可参考，不代表保证；区分客户原话、供应商测算和第三方认证；所有历史型号替换为当前在售配置后再报价。

## 四、案例转为知识库文件时的统一字段

每条案例建议拆成一份独立 Markdown，并保留以下 YAML 或正文头字段：

- `platform`：平台或场景；
- `case_type`：官方原生 / 权威媒体 / 第三方实测 / 跨平台适配参照；
- `brand`、`product`、`scene`、`audience`；
- `published_at`、`verified_at`；
- `source_url`；
- `title_mechanism`；
- `content_structure`；
- `visual_rhythm`；
- `evidence`；
- `cta`；
- `risk_and_limits`；
- `reuse_notes`：只记录结构，不存整篇转载正文。

推荐文件名：`平台_主题_品牌或产品_发布日期_案例卡.md`。若页面是持续更新的产品页，日期改用 `verified-YYYYMMDD`。

## 五、研究结论

1. PC 软文最有效的主线不是“参数很多”，而是“一个人完成一个任务时少了哪些步骤”。
2. 参数必须靠近使用场景，并附配置、系统版本和测试条件；把脚注从页面底部搬回结论附近。
3. 同一个事实不能机械改成十三种口吻：知乎需要选择逻辑，B站需要测试过程，小红书需要生活过程，微博需要节点，朋友圈需要咨询承接，企业方案需要验收指标。
4. 品牌官方内容适合确认“说了什么”，第三方实测适合观察“怎样验证”；两类证据不能互相冒充。
5. 微信视频号、直播间和活动页存在链接失效、登录或动态更新问题，知识库应同时记录账号名、发布日期、标题、截图哈希和核验日。
