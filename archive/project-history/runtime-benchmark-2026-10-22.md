# 当前分块流水线与历史串行架构实测对比（2026-10-22）

## 口径

- 当前测试只使用 `.env` 中的 `LLM_API_KEY` 和 `LLM_BASE_URL`，运行配置为 `single`；主测试模型为 `deepseek-v4.1-flash`，另用历史同款 `qwen-plus` 做兼容性与隔离复测。全程未调用魔搭路由或魔搭令牌。
- 测试需求沿用历史基准：为大学新生生成 MateBook D 14 开学季小红书种草文，重点为学习办公与便携性，只使用知识库事实。
- 当前流程为需求理解、知识匹配、文章规划、生成/重写与审核双队列、连贯性编辑、全文事实与合规终审。
- 历史数据直接引用 [`runtime-benchmark-2026-10-21.md`](runtime-benchmark-2026-10-21.md)，没有重新运行或修改旧架构。

本对比反映“当前整套系统相对历史实测”的变化，不是严格的单变量架构实验：历史模型为 `qwen-plus`，当前模型为 `deepseek-v4.1-flash`；知识库版本、图片审核策略和提示词也已变化。当前首轮已有 2 份资料审核缓存，仅新增复核 1 份，因此不是完全无缓存冷启动。

相对历史记录：

- 首轮总耗时减少 163.740 秒，下降 71.6%，约为历史速度的 3.52 倍。由于当前首轮已有部分缓存，这一列只作整体参考。
- 全热缓存总耗时减少 125.623 秒，下降 70.9%，约为历史速度的 3.44 倍；这是更有参考价值的对比。
- 当前架构请求数更多，但能更快完成且通过终审，说明不能只用调用次数判断延迟或交付效率。

## 两套多模型配置轻量选型

使用同一组构造数据，分别检查需求结构化、文章规划、单块生成和带两处预埋事实错误的逐块审核。该测试只用于接口、结构契约和明显事实边界选型，不代表完整文章质量或端到端耗时。

| 配置 | 理解 | 规划 | 生成 | 审核 | 合计 | 结果 |
|---|---:|---:|---:|---:|---:|---|
| 魔搭 `modelscope-v1` | 2.007 s | 5.854 s | 5.936 s | 3.984 s | 17.781 s | 4/4通过 |
| LLM端点 `llm-multi-v1` | 1.520 s | 4.439 s | 10.821 s | 4.049 s | 20.829 s | 4/4通过 |

魔搭本轮共4次HTTP请求，全部一次成功，没有429或重试；因此该轮结果没有把限流误判为模型问题。LLM端点同样4次请求全部成功。LLM配置总计慢3.048秒，但规划模型只使用实际分配的事实，并明确禁止从参数推导性能或体验；魔搭规划仍出现从“触控功能”扩写“学习办公体验”的倾向。两套审核模型都检出了预埋错误，LLM最终配置的审核结果分别准确定位标题和正文。

因此本地与通用OpenAI兼容端点默认选择 `llm-multi-v1`：Qwen3.8 Flash负责理解与规划，DeepSeek V4.1 Flash负责知识摘录与写作，GLM-5.2负责独立审核；三个结构化角色均按实测需要关闭思考模式。魔搭配置继续保留为部署备用，不删除，也不把未来的429计入模型质量失败。

## 保持历史模型不变的复测

为排除主测试更换模型带来的速度影响，又在同一个 `LLM_API_KEY` 端点把当前架构固定为历史使用的 `qwen-plus`。结果分为严格端到端复测和全热证据隔离复测，两者都没有发生 HTTP 错误或 429。

### 严格端到端

| 指标 | 当前架构 + `qwen-plus` |
|---|---:|
| 阻断前耗时 | 26.893 s |
| HTTP 请求 | 2（全部成功） |
| 最终状态 | blocked |
| 阻断位置 | 首份产品事实资料复核 |

`qwen-plus` 返回了 `passed` 和 16 条事实，但把 `facts` 数组元素输出成字符串；当前资料安全契约要求 `{"text":"连续原文"}` 对象。程序没有把结构不符的结果猜测性转换或放行，因此 16 条全部被原文结构校验拒绝，并以“没有可用产品事实”安全阻断。另一次不写缓存的同提示诊断仍返回 16 个字符串，说明这不是接口失败，而是当前提示契约与该模型不兼容。由于严格链路没有进入创作阶段，26.893 秒不能作为整篇生成耗时与历史 177.106 秒直接比较。

### 复用全热证据后的创作链路隔离测试

为继续观察同模型下的双队列速度，测试复用了当前知识库里已经审核通过的 3 份全热证据（14 条事实、2 张图片，复用过程 0 次模型请求），再让 `qwen-plus` 承担需求理解、规划、逐块生成/重写、逐块审核及后续阶段。这个口径只用于分析创作与审核段，不等同于完整端到端运行。

| 指标 | 当前架构 + `qwen-plus` + 全热证据 |
|---|---:|
| 阻断前总耗时 | 126.324 s |
| HTTP 请求 | 26（全部成功） |
| 文章规划完成 | 19.038 s |
| 首个审核通过块（从请求开始） | 21.974 s |
| 首块通过（从队列启动开始） | 2.936 s |
| 分块队列墙钟时间 | 107.285 s |
| 写作模型处理时间合计 | 55.750 s |
| 审核模型处理时间合计 | 88.737 s |
| 若完全串行的处理时间合计 | 144.487 s |
| 因重叠执行节省 | 37.202 s（25.7%） |
| 生成版本 / 审核版本 / 重写 | 13 / 10 / 8 |
| 最终状态 | blocked |

同模型下，双队列的并行收益仍然清楚：累计模型处理时间 144.487 秒被压缩为 107.285 秒墙钟时间，节省 25.7%。首个通过块由历史热缓存下约 39.956 秒提前到 21.974 秒，减少 17.982 秒（45.0%，约 1.82 倍）。

但本轮不能用 126.324 秒宣称“整篇比旧架构更快”：`qwen-plus` 在规划块目标时加入了“全天不断电”“多任务不卡顿”“一碰传”等事实白名单没有直接支持的效果表述，生成与审核随后反复冲突；B2 达到重写上限并在安全删除后正文为空，流水线按规则阻断，未进入连贯性编辑和全文终审。该结果证明了同模型下的队列重叠收益，也暴露了模型与当前结构化提示契约的兼容性问题。

## 结论

- 当前链路使用 `LLM_API_KEY` 端点完成了两轮真实运行，没有发生 429。
- 全热缓存下，总耗时由历史 177.106 秒降至 51.483 秒，且结果从 `blocked` 提升为通过终审的 `review`。
- 分块生成与审核重叠本身稳定节省约 8.2 秒、约 27%；其余总体改善还来自更快的当前模型、知识审核缓存、停止视觉模型审图、提示词与生成—审核闭环优化。
- 固定为历史 `qwen-plus` 后，队列重叠仍节省 37.202 秒、25.7%，首块时间也改善 45.0%；但该模型目前不能完整遵守资料复核和块规划契约，严格链路与隔离链路均安全阻断，所以没有可用于“整篇完成速度”的同模型数据。
- 当前主要剩余延迟集中在文章规划、连贯性编辑和全文终审；继续优化时应保留严格事实门禁，优先减少重复上下文和不必要的终审调用。
