## 知识库实际使用范围

产品事实并非整个 Agent 只读 P1，而是采用“事实层与表达层分权”：

- `Evidence.facts` 只允许来自 P1 的 `product_facts`，用于事实引用和最终核验。
- P1 的 `product_guidance`、P2 话术、P6 营销模板、P7 常见问题、P8 客户场景可进入 `Evidence.context`，只影响表达和场景组织，不能升级为产品事实。
- 每轮默认最多选择 2 份表达参考（`reference_limit=2`）。
- 图片从已登记且与型号绑定的图片记录中选择，每轮目标最多放行 2 张（`image_limit=2`）。
- 动态价格记录不进入普通表达参考；当前策略也禁止历史价格作为事实使用。

## 发现的问题

1. MateBook D 14 的产品事实仍标记为“迁移候选，尚未完成人工事实复核”。尺寸字段把 `15.9 mm` 放在“长度”、`227.79 mm` 放在“厚度”；运行时规则已排除这两个值，但源数据需要修正。
2. 四张已审 MateBook D 14 图片均被模型判为 `uncertain`，原因主要是图片本身不能证明型号年份或“护眼”等功能，且部分原始来源页已失效。因此小红书要求至少 3 张图，而本轮 0 张可用。
3. 热缓存时，已缓存但未通过的图片不会满足 `image_limit`，循环会继续审核后续未缓存图片。第二轮因此新增两次图片调用，耗时约 26.16 秒；后续运行还可能继续扫描剩余候选。
4. 初稿与改写持续产生无事实支撑的场景推论或绝对化表达，三轮核验后仍有错误。冷启动首轮 8 个阻断项，热缓存首轮 13 个阻断项；自动删除后仍分别剩 3 个和 1 个阻断项。
5. 事实核验与合规核验当前串行执行，但二者输入独立，是主要延迟来源。

## 优化优先级

1. **先修生成—核验闭环。** 把高频错误模式前置到写作/改写提示词，并让改写严格逐项覆盖审核意见；否则每次都付出三轮核验成本且仍可能 blocked。这既是速度问题，也是交付成功率问题。
2. **并行事实与合规核验。** 两项检查互不依赖。按热缓存实测，同轮并行的理论耗时可由两者相加降到取最大值，四次检查合计约可从 113.37 秒降到 64.85 秒，理论节省约 48.5 秒（不含并发限流风险评估）。
3. **修正图片候选补位逻辑。** 为“一次创作最多审核多少张候选图”设置稳定上限，缓存 `uncertain/rejected` 后不要在每次请求中继续向后扫描；更适合在离线预热任务中批量审图。
4. **预热首次使用审核。** 新库上线前离线完成高频型号的 P1、平台模板、场景卡和图片审核。冷启动本次仅知识库审核就用了 95.94 秒。
5. **先清理知识库源数据。** 修复尺寸字段、失效来源和图片归属证据，减少严格审核排除及后续无效调用。
6. **缩小审核上下文。** 在写作前先按用户关注点筛选事实，核验时只发送稿件实际引用的事实与相关原文，减少大上下文响应时间。

## 基准结论

- `.env` LLM 端点：真实串行负载下可用，本轮无 429。
- 新库运行机制：连接、P1 事实提取、跨层参考选择和缓存均工作。
- 新库内容状态：尚不能视为完全验收，存在字段错位、来源失效和图片无法确证问题。
- Agent 交付状态：当前严格模式下未能完成定稿；下一步应优先优化核验闭环和图片审核策略，而不是先优化毫秒级的本地检索。
