# 知识库与模型运行约定

本文件同时说明当前代码行为与目标运行约定，避免在代码迁移期间混淆。目标流程以 [核心架构规范](core-architecture.md) 为准，实施进度见 [项目进度](../ROADMAP.md)。未标注“目标”的段落描述当前实现。

核心链路为：需求澄清与规范化 → 当前知识审核 → 现有上下文输入 → 生成/重写模型与审核模型之间的分块队列 → 事实锁定的整文连贯性编辑 → 全文终审 → 用户确认、归档与导出。分块队列、连贯性编辑和终审已经启用；统一上下文契约与官网知识时效门禁尚未启用。

## 数据与存放位置

唯一运行目录为 `knowledge_base/current`，可通过 `KB_LOCAL_DIR` 指定同结构的实际位置。原库、旧快照、迁移工具和无效内容均已删除；项目历史资料单独存放在 `archive/`，不参与运行。

当前包含1220条资料：产品75、生态及支持172、人群场景162、营销表达452、图片95、动态信息86、竞品资料178。新增的12张生态协同能力卡已经通过文件与索引结构校验，但仍标记为待人工事实复核。可生成主推产品仍为10个已有完整事实的PC型号；55份扩展产品发现卡不能替代正式规格。竞品资料只在明确比较意图下提供对比框架和待核线索，对外竞品事实仍需重新打开对应品牌官网核对。

图片中88张有精确型号登记，可进入自动配图；7张通用素材只供人工挑选。待确认、错位隔离和旧销售快照均不保留。动态信息包含66条历史价格及20份业务登记/复核模板：历史价格可用于趋势与追溯，但不能作为当前价格；模板不含实际值。画像、范文、排障、竞品参考和营销参考不作为主推产品事实。

来源、行号、哈希、来源纠正和图片原索引记录保留在 `00-规范与索引/catalog.json`，产品来源表保留在该目录的 `来源登记/`，它们是必要追溯数据。内容治理只维护 `治理与使用规范.md`，`runtime-policy.json` 保存执行参数，`usage-review.sqlite3` 保存审核标记；`派生视图/产品横向检索.json` 从产品事实自动生成，不作为第二事实源。

## 当前审核与复用

入库由外部负责。本项目执行：检索相关文字资料 → 检查版本与审核标记 → 仅审核未检查或已变化的文字资料 → 保存结论 → 读取精确型号已登记图片 → 写作 → 核验当前稿件。

文字审核记录绑定文件、标注、型号/配置、来源、相关产品依据、提示词、模型与规则版本。未变化则复用；文件修改需同步对应来源与catalog哈希，未同步则拒绝读取。原文只读，标记写入独立审核索引。图片不写模型审核记录。

`passed`表示内部一致性与使用边界复核允许使用，不代表官网、授权或人工复核已经完成。`uncertain/rejected`复用为排除结果。失败或中断不得写成通过；并发请求先持久化占位，避免重复调用。

`python tools/knowledge_review.py` 查看当前标记。查明原因后，可用 `--reset 缓存key` 清除某条非通过记录，供下次使用重审；不自动发请求，不清除通过记录。

产品摘录必须能还原成连续原文；只允许排版空白差异，不接受改写。可疑尺寸字段停止使用，确认后才可修正。参考资料只提供表达与问题提示。每篇稿件仍检查当前型号、适用条件、图注与图文对应，素材曾通过不代表适合所有文章。

## 目标知识安全门禁

知识库仍在整理，具体有效期数值暂不写死。整理完成后，按资料类型配置有效期，并为事实资料记录来源 URL、入库时间、最近官网核验时间、有效期或失效时间、适用范围、核验模型和结论。

新入库资料、首次实际调用但没有有效核验记录的资料，以及距上次调用或核验超过有效期的资料，均交给专用知识核验模型执行官网文字核验。文件、来源、型号/SKU、适用范围、规则、提示词或模型变化时同样使旧结果失效。核验模型只能比较文字与来源，不从图片推导事实。

官网核验必须记录来源 URL、访问时间、对应原文、差异与 `passed / uncertain / outdated / rejected / failed / in_progress` 状态。只有内部一致性审核和官网时效核验均有效的资料，才能作为当前产品事实进入写作。

发现过时或错误资料时，先生成包含旧值、新值、适用范围、来源和差异的候选修订，不静默覆盖正式事实。低风险且来源明确的变更可按受控规则更新；型号/SKU、价格权益、地区渠道、相互冲突来源或大范围删除必须人工确认。更新后同步来源、哈希、派生视图和核验记录，旧版本只作隔离追溯。

## 模型职责

当前代码提供两套多模型路由和一套单模型兼容模式。`LLM_PROFILE=llm-multi-v1` 使用 `LLM_API_KEY` 端点，当前分工为：

| 模型 | 职责 |
|---|---|
| qwen3.8-flash | 需求理解、修改意图、文章分块规划与事实白名单分配；结构化阶段关闭思考模式 |
| deepseek-v4.1-flash | 首次资料内部复核与原文摘录、内容块生成/重写、整文连贯性编辑 |
| glm-5.2 | 逐块事实与合规审核、连贯性事实锁、全文事实与合规终审；关闭思考模式 |

`LLM_PROFILE=modelscope-v1` 继续使用 `config/model_routing.json` 中的魔搭三角色配置；`LLM_PROFILE=single` 则由 `LLM_MODEL` 指定的单个模型承担所有阶段。三种模式共享相同的阶段名、输入权限和输出契约，物理模型变化不能绕过事实门禁。

目标逻辑角色：

| 角色 | 职责 |
|---|---|
| 需求理解模型 | 多轮澄清、结构化需求和修改意图；规范任务说明由程序确定性生成 |
| 知识核验模型 | 官网文字核验、时效判断、差异与候选修订 |
| 生成/重写模型 | 按块生成、接收审核退回任务后按块重写，以及受事实锁定约束的整文连贯性编辑 |
| 审核模型 | 并行消费内容块，执行事实、夸大与合规检查；所有块通过后执行全文终审 |

一个物理模型可以承担多个角色，但输入权限、提示词与输出契约必须隔离。分块生产中，生成/重写与审核是两个独立角色；审核模型不直接修改内容，而是把未通过块连同结构化问题送回生成/重写队列。

图片暂不发送给视觉模型。运行时仅使用 `registered_image`、精确绑定当前型号且文件哈希与索引一致的素材；通用素材不自动使用。图片登记说明只用于选图和中性图注，不能作为产品参数、性能或效果依据。

目标写作上下文统一包含已确认事实、卖点宣传模板、图片登记说明、门店偏好和按效果权重选出的历史优秀作品。只有产品事实拥有事实证据权限；其余内容只影响角度、结构、语气与行动引导。当前代码已经支持表达参考、图片、用户偏好和加权历史作品的部分注入，但继续沿用原有输入方式；待知识库整理完成后再收拢为统一上下文契约。

分块计划为每块指定目标、顺序、依赖关系和可用事实白名单。生成/重写模型把块送入审核队列；审核模型通过后冻结该版本，未通过则送回重写队列。相互独立的块允许生成和审核重叠执行，以缩短总体等待时间；有上下文依赖的块等待前置块通过。所有块通过后执行整文连贯性编辑，程序先检查段落、事实编号、图片、标签和数字锁，审核模型再比较编辑前后的语义事实；任一事实锁失败就整次回退，之后再对完整文章和图注进行终审。

## 成本与维护

当前实现默认每轮最多新增3次文字知识复核：产品事实1份、表达参考最多2份。图片最多选2张但不调用模型。缓存齐备后不重复文字资料审核；需求、写作和成稿核验照常。可通过 `KB_REVIEW_MAX_CALLS`、`KB_REFERENCE_LIMIT`、`KB_IMAGE_LIMIT` 收紧数量。

魔搭分工模式关闭JSON自动修复，并对接口突发限流保留有限重试；LLM端点分工模式允许一次JSON纠正调用，并保留有限的瞬时错误重试。分块队列按内容块分别记录版本和重写次数，每块最多重写两轮；达到上限后只允许定位明确的安全删除并重新审核，否则阻断该块。审核结果携带块版本，过期结果不能覆盖新版本。没有已登记图片时明确说明，不编造素材凑数。

新流水线重点观察首块可见时间、整篇完成时间、生成/审核/重写队列等待时间、重写率与模型消耗，并与当前整篇串行链路对照。并行只用于满足依赖条件的内容块，不以牺牲上下文正确性换取速度。

`python tools/validate_knowledge_base.py` 校验当前库的文件、索引与内部链接，无需旧库，不调用模型。

当前库 `knowledge_base/current` 随仓库发布，令牌和运行时审核数据库不提交。`archive/` 仅保存必要的项目发展记录，不进入部署与检索。部署时让审核索引所在目录可写且持久化。模型或提示词调整后重启应用。
