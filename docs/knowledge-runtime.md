# 知识库与模型运行约定

本文件说明当前代码行为与运行约定。整体流程以 [核心架构规范](core-architecture.md) 为准，实施进度见 [项目进度](../ROADMAP.md)。

核心链路为：需求澄清与规范化 → 知识库读取与确定性校验 → `writing-context-v1` 统一上下文 → 生成/重写模型与审核模型之间的分块队列 → 事实锁定的整文连贯性编辑 → 全文终审 → 用户确认、归档与导出。上述环节均已启用，创作检查点可在进程中断后由用户显式恢复。

## 数据与存放位置

唯一运行目录为 `knowledge_base/current`，可通过 `KB_LOCAL_DIR` 指定同结构的实际位置。原库、旧快照、迁移工具和无效内容均已删除；项目历史资料单独存放在 `archive/`，不参与运行。

当前包含2520条资料：产品190、生态及支持197、人群场景162、营销表达495、图片852、动态信息446、竞品资料178。已登记53个型号/系列；84份扩展产品发现卡不能替代正式规格。竞品资料只在明确比较意图下提供对比框架和待核线索，对外竞品事实仍需重新打开对应品牌官网核对。

图片中845张有精确型号登记，可进入自动配图；7张通用素材只供人工挑选。待确认、错位隔离和旧销售快照均不保留。动态信息包含426条历史价格及20份业务登记/复核模板：历史价格可用于趋势与追溯，但不能作为当前价格；模板不含实际值。画像、范文、排障、竞品参考和营销参考不作为主推产品事实。

来源、行号、哈希、来源纠正、生命周期和图片原索引记录保留在 `00-规范与索引/catalog.json`，产品来源表保留在该目录的 `来源登记/`，它们是必要追溯数据。`source.locator_type` 区分 `local`、`url`、`historical` 三种来源位置；`historical` 只保留旧库追溯信息，不代表当前仍可读取。内容治理只维护 `治理与使用规范.md`，`runtime-policy.json` 保存执行参数，`knowledge-verification.sqlite3` 保存历史核验结论与候选修订；`派生视图/产品横向检索.json` 从产品事实自动生成，不作为第二事实源。

## 当前知识库读取

入库由外部负责。本项目执行：检索相关文字资料 → 校验型号、哈希与尺寸字段 → 读取精确型号已登记图片 → 写作 → 核验当前稿件。

运行时完全信任知识库，知识库阶段不调用任何模型：

- 产品事实：读取 `产品事实.md`，按“小节 + 字段”拼成连续原文作为事实点，剔除明显异常的尺寸字段。
- 表达参考：平台模板、同型号成稿、角色沟通卡直接取正文进入写作上下文。
- 保留的确定性校验：catalog 与文件哈希一致性、型号归属、异常尺寸字段剔除、事实冲突检测。

知识库阶段没有模型调用，匹配耗时在 1 秒以内，剩下的时间全部是写作与成稿审核。

产品摘录必须能还原成连续原文；只允许排版空白差异，不接受改写。可疑尺寸字段停止使用，确认后才可修正。参考资料只提供表达与问题提示。每篇稿件仍检查当前型号、适用条件、图注与图文对应，素材曾通过不代表适合所有文章。

## 保留的确定性校验

- `catalog.json` 与知识库文件 sha256 一致，否则拒绝使用；
- 资料型号必须与当前主推型号精确对应；
- 明显异常的尺寸字段（厚度、长度）整节剔除，不进入事实点；
- 检测产品事实之间的冲突，存在冲突时阻断生成。

生命周期元数据（资料类型、入库时间、来源 URL/日期、TTL）仍保留在 catalog 中作为追溯信息，运行时不强制执行时效核验。`knowledge-verification.sqlite3` 中的历史核验结论与候选修订仅供追溯，不参与运行时判断。

运维命令：

```bash
python tools/knowledge_verify.py --list          # 查看历史核验记录
python tools/knowledge_verify.py --candidates    # 查看待人工批准的知识修订
```

## 模型职责

当前代码提供两套多模型路由和一套单模型兼容模式。`LLM_PROFILE=llm-multi-v1` 使用 `LLM_API_KEY` 端点，当前分工为：

| 模型 | 职责 |
|---|---|
| qwen3.8-flash | 需求理解、修改意图、文章分块规划与事实白名单分配；结构化阶段关闭思考模式 |
| deepseek-v4.1-flash | 内容块生成/重写、整文连贯性编辑 |
| glm-5.2 | 逐块事实与合规审核、连贯性事实锁、全文事实与合规终审；关闭思考模式 |

`LLM_PROFILE=modelscope-v1` 继续使用 `config/model_routing.json` 中的魔搭三角色配置；`LLM_PROFILE=single` 则由 `LLM_MODEL` 指定的单个模型承担所有阶段。三种模式共享相同的阶段名、输入权限和输出契约，物理模型变化不能绕过事实门禁。

逻辑角色：

| 角色 | 职责 |
|---|---|
| 需求理解模型 | 多轮澄清、结构化需求和修改意图；规范任务说明由程序确定性生成 |
| 生成/重写模型 | 按块生成、接收审核退回任务后按块重写，以及受事实锁定约束的整文连贯性编辑 |
| 审核模型 | 并行消费内容块，执行事实、夸大与合规检查；所有块通过后执行全文终审 |

一个物理模型可以承担多个角色，但输入权限、提示词与输出契约必须隔离。分块生产中，生成/重写与审核是两个独立角色；审核模型不直接修改内容，而是把未通过块连同结构化问题送回生成/重写队列。

图片暂不发送给视觉模型。运行时仅使用 `registered_image`、精确绑定当前型号且文件哈希与索引一致的素材；通用素材不自动使用。图片登记说明只用于选图和中性图注，不能作为产品参数、性能或效果依据。

写作上下文使用 `writing-context-v1` 契约，统一包含规范任务说明、已确认事实、卖点宣传模板、图片登记说明、用户偏好和按效果权重选出的历史优秀作品，以及场景、平台、来源清单与核验摘要。契约明确声明：只有已核验产品事实拥有事实证据权限；模板、偏好和历史作品只能影响角度、结构、语气与行动引导。上下文保存在会话检查点中，供规划、分块生成、恢复和回退复用；产品或策略变化时按影响范围重新装配。

分块计划为每块指定目标、顺序、依赖关系和可用事实白名单。生成/重写模型把块送入审核队列；审核模型通过后冻结该版本，未通过则送回重写队列。相互独立的块允许生成和审核重叠执行，以缩短总体等待时间；有上下文依赖的块等待前置块通过。所有块通过后执行整文连贯性编辑，程序先检查段落、事实编号、图片、标签和数字锁，审核模型再比较编辑前后的语义事实；任一事实锁失败就整次回退，之后再对完整文章和图注进行终审。

## 成本与维护

表达参考按类型分名额（`reference_slots`）：`platform` 平台图文模板1份、`copy` 同型号成稿或任务卡1份、`audience` 人群场景卡或角色沟通卡1份。三类名额互不挤占，某类没有匹配资料时该名额留空，不拿其他类型补位。图片默认最多选8张；已通过块用过的图片不会重复提供给后续块。可通过 `KB_REFERENCE_LIMIT`（总名额）、`KB_IMAGE_LIMIT` 收紧数量。

魔搭分工模式关闭JSON自动修复，并对接口突发限流保留有限重试；LLM端点分工模式允许一次JSON纠正调用，并保留有限的瞬时错误重试。模型输出达到长度上限时会自动提高输出额度并要求精简后重试。分块队列按内容块分别记录版本和重写次数，每块最多重写两轮；达到上限后只允许定位明确的安全删除并重新审核，否则阻断该块。审核结果携带块版本，过期结果不能覆盖新版本。没有已登记图片时明确说明，不编造素材凑数。

新流水线重点观察首块可见时间、整篇完成时间、生成/审核/重写队列等待时间、重写率与模型消耗，并与当前整篇串行链路对照。并行只用于满足依赖条件的内容块，不以牺牲上下文正确性换取速度。

创作过程按阶段写入工作台数据库检查点。进程中断时，尚处于 `generating/reviewing` 的内容块在恢复时回到 `pending_generate`，已经审核通过并冻结的块继续复用。恢复必须由用户在页面显式触发，服务重启不会自行调用模型。运行日志只记录状态、耗时、请求数和 token 计量，不保存凭证、提示词或模型正文。

`python tools/validate_knowledge_base.py` 校验当前库的文件、索引、生命周期元数据、来源位置与内部链接，无需旧库，不调用模型。`python tools/review_capability_cards.py` 可重复核验25份生态能力卡的228条官网引文；自动结果只标为 `source_verified`，不替代人工事实批准。

当前库 `knowledge_base/current` 随仓库发布，令牌和运行时审核数据库不提交。`archive/` 仅保存必要的项目发展记录，不进入部署与检索。部署时让 `00-规范与索引/` 可写且持久化，并备份两个 SQLite 索引。模型或提示词调整后重启应用。
