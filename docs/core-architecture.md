# 软文智能体核心架构规范

本文定义项目后续实现、测试和文档说明必须共同遵循的核心架构。它描述目标状态，不表示所有模块已经完成；实际进度见 [项目进度](../ROADMAP.md)，当前代码行为见 [知识库与模型运行约定](knowledge-runtime.md)。

## 1. 目标与原则

系统接收自然语言需求，通过多轮对话把创作目的澄清为结构化数据，再将结构化数据转写为无歧义的规范任务说明。系统只从通过安全门禁的知识中选择产品事实、卖点宣传模板和产品图片，并同时使用门店偏好与按效果权重选出的历史优秀作品作为写作参考。

软文生产采用两个模型之间的分块队列流水线：生成/重写模型负责按块写作，审核模型负责逐块检查；需要修改的块由审核模型送回重写队列。各块通过后，再进行不改变事实的整文连贯性编辑和全文终审。该设计的首要目的，是让生成与审核重叠执行，减少串行完成整篇后再审核造成的总体等待时间。

全链路遵循以下边界：

- 产品事实、参数、能力、价格、权益和适用条件只能来自当前有效且可追溯的事实资料。
- 宣传模板、门店偏好和历史优秀作品只影响选题、结构、语气与行动引导，不能升级为事实证据。
- 图片必须具有可验证的来源和产品归属；图片本身不能证明画面外的性能、效果或承诺。
- 模型负责理解、生成、审核和提出修订，程序负责状态流转、权限边界、证据绑定、重试上限和留痕。
- 用户未明确确认前，稿件始终是会话草稿；只有确认后的版本才能写入历史作品库。

## 2. 端到端流程

```text
用户自然语言输入
  ↓
多轮需求澄清 ── 信息不足 ──▶ 继续追问
  ↓ 目的明确
结构化需求
  ↓
规范任务说明（结构化数据的确定性自然语言表达）
  ↓
知识读取与确定性校验：型号归属、哈希一致、异常尺寸剔除、事实冲突
  ↓
上下文装配：产品事实 + 卖点宣传模板 + 产品图片
            + 门店偏好 + 加权历史优秀作品
  ↓
文章规划：确定分块、块间依赖、每块目标和允许使用的事实
  ↓
生成队列 ─▶ 生成/重写模型 ─▶ 审核队列 ─▶ 审核模型
   ▲                                      │
   └──────────── 需要重写的块 ────────────┘
                                          │ 通过
                                          ▼
                                  已通过块集合
  ↓ 全部块通过
整文连贯性编辑（不得新增、删除或改变事实）
  ↓
全文事实、夸大、合规、图片与结构终审
  ↓
用户确认 ── 修改要求 ──▶ 按影响范围回到对应阶段
  ↓ 确认
保存历史作品 + 提供多格式下载
```

## 3. 需求与上下文

### 3.1 多轮澄清

至少明确产品、目标受众、使用场景、发布平台和创作目标。购买阶段、核心问题、语气、篇幅、活动信息及临时要求按任务补充。字段存在不等于目的明确；如果型号、目标、对象或约束仍有歧义，系统必须继续追问。

### 3.2 规范任务说明

结构化需求确认后，生成一份规范自然语言说明，作为后续检索、规划、生成、审核和回退时的共同任务定义。该说明必须完整表达结构化字段，不得补入用户未确认的事实，并与原始结构化数据同时留存。

### 3.3 上下文装配

进入写作模型前，统一装配以下五类输入：

| 输入 | 作用 | 证据权限 |
|---|---|---|
| 产品事实 | 支撑参数、功能、限制和适用条件 | 可以作为事实证据 |
| 卖点宣传模板 | 提供卖点组织、内容结构和平台表达方式 | 不可作为事实证据 |
| 产品图片 | 提供已登记、已绑定型号的配图候选 | 只证明登记范围与可见画面 |
| 门店偏好 | 约束语气、重点客群、常用平台、内容偏好和禁区 | 不可作为事实证据 |
| 加权历史优秀作品 | 参考高表现作品的角度、结构和行动引导 | 不可作为事实证据，不得照搬无依据内容 |

历史作品权重至少考虑宣传效果、样本可信度，以及平台、场景、受众、目标和产品相似度。权重用于排序参考价值，不覆盖当前任务、平台规则或事实资料。

## 4. 双模型分块队列流水线

### 4.1 模型职责

分块生产只包含两个逻辑角色：

- **生成/重写模型**：按文章规划生成新块；收到重写任务时，仅根据审核问题和允许事实修改指定块。
- **审核模型**：检查每个块的事实性、适用条件、过度夸大、营销合规、事实编号和与已通过相邻块的衔接；通过或生成结构化重写任务。

同一个生成/重写模型承担初次生成和问题重写，以减少口径漂移。审核模型不直接润色或暗改正文，只返回审核结论与可执行的问题清单。

### 4.2 队列与状态

每个内容块拥有独立标识、顺序、目标、事实白名单、依赖块、版本和重写次数，状态只能按以下规则流转：

```text
pending_generate → generating → pending_review → reviewing → passed
                                      │
                                      └─▶ pending_rewrite → generating

达到重写上限、证据冲突或无法安全改写 → blocked
```

- 生成队列同时容纳首次生成任务和审核退回的重写任务。
- 审核队列只接收带版本号的完整块；过期版本的审核结果不得覆盖新版本。
- 不依赖前文的块可以继续生成；依赖已通过前文的块必须等待依赖满足。
- 审核通过的块进入只读集合，除非用户修改影响到该块，不能被后续块悄然改写。
- 重写任务必须指出问题位置、问题类型、证据冲突和允许的处理方式；无法安全修正时删除主张或阻断，不得用另一个未经证实的说法替换。
- 达到重写上限仍未通过时停止合并，向用户或人工审核暴露原因，不能把问题块混入成稿。

### 4.3 并行与顺序

流水线追求的是生成与审核的时间重叠，不是无条件并发所有内容。标题、导语或需要引用前文结论的块可设置依赖；相互独立的卖点块、场景块可以排队生成，并在前一块进入审核后开始下一块。队列并发度、重写优先级和在途块数量应可配置并接受压测。

### 4.4 整文连贯性编辑

全部内容块通过后，由编辑模型处理段落顺序、过渡、指代、语气一致性和重复表达。编辑模型只能使用已通过块及其事实编号，不得：

- 新增或改变产品事实、数字、型号、价格、权益、承诺和适用条件；
- 删除使某项事实成立所必需的限定条件；
- 把历史作品、模板、偏好或图片描述变成产品事实；
- 引入新的事实编号或知识材料。

编辑结果必须再次执行全文终审。逐块通过不能替代全文检查，因为块与块组合后仍可能出现条件冲突、重复承诺或指代错误。

## 5. 知识库读取与校验

### 5.1 运行时读取

运行时完全信任知识库，知识库阶段不调用任何模型，也不抓取官网：

- 产品事实：读取 `产品事实.md`，按“小节 + 字段”拼成连续原文作为事实点。
- 表达参考：平台模板、同型号成稿、角色沟通卡直接取正文进入写作上下文。
- 图片：只使用 catalog 中已登记、绑定当前精确型号且哈希一致的图片。

### 5.2 保留的确定性校验

- `catalog.json` 与知识库文件 sha256 必须一致，否则拒绝读取；
- 资料型号必须与当前主推型号精确对应；
- 明显异常的尺寸字段（厚度、长度）整节剔除，不进入事实点；
- 产品事实之间出现冲突时阻断生成。

生命周期元数据与历史核验结论保留在 catalog 和 `knowledge-verification.sqlite3` 中，只用于追溯，不参与运行时判断。

### 5.3 知识修订

发现过时或错误时，不允许模型静默覆盖正式事实。系统先形成候选修订，至少包含旧值、新值、适用范围、来源 URL、核验时间、差异说明和建议动作。

- 来源明确、范围不变且规则允许的低风险更新，可以按受控流程写入当前知识并保留旧值审计记录。
- 涉及型号/SKU、价格权益、地区渠道、法律合规、互相冲突的官方来源或大范围删除时，必须等待人工确认。
- 修订完成后同步更新来源、哈希、派生视图和核验记录；旧记录不能继续被运行时复用。
- 历史资料可保留作追溯，但必须与当前可调用知识隔离。

运行时完全信任知识库：知识库阶段不调用模型，也不抓取官网。产品事实按原文取用，参考资料直接进入写作上下文；保留 catalog 与文件哈希一致、型号归属、异常尺寸字段剔除和事实冲突检测等确定性校验。

## 6. 多模型分工

项目采用按职责路由的多模型架构，逻辑角色至少包括：

| 角色 | 职责 |
|---|---|
| 需求理解模型 | 多轮澄清、结构化需求、修改意图识别；规范任务说明由程序确定性生成 |
| 文章规划模型 | 将规范需求与事实白名单拆成内容块、依赖关系和块级事实权限，不负责发挥文案 |
| 生成/重写模型 | 内容分块生成、审核退回块重写、受约束的整文连贯性编辑 |
| 审核模型 | 逐块事实与夸大审核、全文终审 |

一个物理模型可以承担多个逻辑角色，但路由、提示词、输入权限和输出契约必须按角色隔离。审核模型与生成/重写模型在分块流水线中必须是两个独立角色，不能让同一次生成调用自行宣布通过。

## 7. 用户确认与按需回退

用户提出修改时，根据影响范围回到最早受影响阶段，并尽量复用仍然有效的产物：

| 用户要求 | 回退位置 | 可复用内容 |
|---|---|---|
| 调整措辞、长短或语气 | 对应内容块的生成队列 | 需求、有效知识、规划和未受影响的已通过块 |
| 调整某个卖点或图片 | 上下文装配或对应内容块 | 未受影响事实和内容块 |
| 更换场景、受众、平台或目标 | 策略/模板匹配与文章规划 | 仍适用的产品事实与图片 |
| 更换产品或型号 | 需求确认与知识匹配 | 仅保留无产品绑定的用户偏好 |
| 资料过期或事实冲突 | 知识安全门禁 | 与冲突无关且仍有效的资料 |

每次回退都要使受影响的下游结果失效；不得让旧块、旧审核结论或旧连贯性编辑结果混入新版本。

## 8. 确认、历史作品与导出

只有逐块审核、连贯性编辑和全文终审全部通过的稿件才能进入用户确认。确认前可继续按上述规则回退；明确确认后，系统才：

1. 保存最终稿、结构化需求、规范任务说明、事实引用、图片登记和审核轨迹；
2. 写入历史作品库，后续宣传效果数据与作品版本关联；
3. 提供 Markdown、DOCX、PDF 等发布成品和完整溯源报告下载。

用户之后可以编辑或删除已归档作品；编辑时应保留最初审核版本与修改记录，删除时同步删除关联宣传数据。未经重新审核的编辑内容不能反向污染知识库或直接成为事实参考。只有至少一项有效宣传指标大于零的历史作品可以参与后续表达策略参考；没有宣传记录或只有全零记录的作品不得进入生成上下文。

## 9. 验收指标

后续实现至少验证：

- 首块可见时间、整篇完成时间，以及相对整篇串行生成/审核的耗时改善；
- 生成队列、审核队列、重写队列的等待时间、吞吐量和重写率；
- 分块事实错误漏检率、过度夸大漏检率、误报率和达到上限后的阻断率；
- 连贯性编辑前后事实集合是否保持不变；
- 新资料、过期资料、官网冲突和修订记录能否正确触发、隔离和追溯；
- 用户回退后是否只复用仍有效的上游结果；
- 历史作品和门店偏好是否影响表达而不进入事实证据链。
